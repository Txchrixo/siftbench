# Proofline campaign protocol

The official starter is pinned at `79d03777827b88aa23ee9309ebefab5f9766cd09`. Review inputs use its app-only branches. The campaign uses the same eight code-only cases for Proofline and Greptile, plus one paired snapshot experiment on case 05. This produces 16 main observations and two additional snapshot observations. The snapshot condition keeps the same application head and appends the supplied simulation record to the original PR body.

Each provider and condition gets a new private repository. Seed only the pinned app-only refs and grant access only to the designated reviewer. The working copy, rubric, and review captures stay outside those repositories. Check each installation and its automatic review settings before opening any PR. Record visible settings, quota limits, and soft failure signals. Use product defaults for review sensitivity and avoid feedback, automated fixes, and automatic approval during measurement. Reviewers may have prior exposure to the public case branches or retain cross-repository context beyond the available settings. The original pilot also covered a related pagination failure. Treat the official case 01 result as a measurement on the shared case, without claiming it is a held-out task.

Capture the first review published by the verified GitHub actor on the pinned head, with a 30-minute deadline and a 30-second settling window. Record explicit quota signals when present. A missing submission is an incomplete observation. If the same commit was reviewed on another PR, use the publication on the current PR. Preserve the raw source locally and link to it from the report. Compare providers on their shared completed cases and retain pending, failed, quota-limited, and unattempted pairs in coverage.

## Scoring

- Credit a concrete, reproducible finding that matches the pinned rubric. Mark another independently verified issue as a novel finding.
- Mark repeated versions of the same finding as duplicates. Treat descriptive summaries with no actionable claim as out of scope. Use the export without source URLs for grading and disclose that wording and badges can still reveal the provider.
- For code-only cases 04, 05, and 06, a specific request for missing deployment evidence can earn credit as a justified context request. For case 04, the relevant evidence is active readers of the retired column. For case 05, it is the receiver's effective per-request limit and observed batch size. For case 06, it is which workers subscribe to the new queue. A categorical claim about a particular deployment requires evidence of that deployment.
- Case 07 has no expected functional defect from the visible index change. Verify any reported side effect before deciding. Case 08 has no expected defect in the app-only scope. A separate starter smoke check depends on the old exact summary shape and must be interpreted using the files actually visible to the reviewer.
- The snapshot observation for case 05 requires identifying the affected site and the evidence establishing its limit. The snapshot is simulated. A separate verified AWS invocation can establish behavior of the deployed starter workload at its recorded revision.
- Preserve uncertainty when a claim cannot be validated. Calculate recall against checked reference findings only and report justified context requests, duplicates, unresolved claims, and repeat runs separately.
